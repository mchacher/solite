# Architecture

How Solite is built **today**. Short: the blocks, where they run, how data flows. Only what
exists: the target architecture is decision D1, and what comes next is in the roadmap.

## Overview

```
          crates/core  (Rust library: name, version, banner, memory line;
                        radio/: ASH, EZSP, ZDO, ZCL, the coordinator;
                        engine/: the radio loop and the saver; no socket, no
                        clock, no random source, no file)
                  │                         │
     crates/host (Rust, Mac)          firmware/ (Rust std on ESP-IDF, ESP32)
     prints the banner; with          banner, memory, data partition (FAT),
     --radio, TCP transport ──► Dongle Max's radio (original firmware, port 6638)
     files in a folder                network setting; feature sim: the engine on
                                      crates/sim; booted on the Mac in
                                      Espressif's QEMU (scripts/qemu.sh);
                                      feature radio: the engine on the real radio
                                      over UART1 (the radio image)

     ui/ (Preact + TypeScript, browser): the rooms and equipments, live;
         served from ui/dist by the host's --serve, or from the radio
         image's flash, through /api and /ws

     tools/z2m-coverage (Node, Mac only): Zigbee2MQTT's library → report.md
```

The core has no hardware or operating-system dependency: the same code is compiled for the Mac
(`aarch64`/`x86_64`) and for the ESP32 (`xtensa-esp32-espidf`). The interface is a separate web
app, built by Vite into `ui/dist`, which the host's `--serve` serves from disk and the radio image embeds, compressed, in its flash.

| Core | The Sowel core: shared by every program, no hardware. `radio/`: the ASH frame layer, the EZSP commands and callbacks, ZDO and ZCL frames, the generic reading of the standard clusters' measures (`measures.rs`), and the coordinator (start or resume the network, pairing, identifying a device, setting up its reporting, enrolling alarm devices, listening to its measures, sending commands and waiting for their acknowledgement in `commands.rs`), as state machines fed with bytes, time and random bytes; ## Builds

- **Mac workspace** (`Cargo.toml` at the root): `crates/core`, `crates/host`, `crates/recipe-sdk`,
  `crates/sim`, `crates/ui-embed`; Rust stable pinned
  in `rust-toolchain.toml`.
  `rquickjs` 0.14.0 (QuickJS-ng, its C sources compiled by the build, no OS) is a dependency of the core
  behind the feature `script-recipes` (the host always enables it); its crate `rquickjs-sys` is
  vendored under `vendor/rquickjs-sys` (MIT licence kept, `vendor/rquickjs-sys/SOLITE.md` lists the
  changes: the small-object arena off, about 85 KB per runtime, no copy of each function's source)
  and patched in through `[patch.crates-io]` in the root `Cargo.toml` and in `firmware/Cargo.toml`;
  it is built at `opt-level = 3` in the dev profile too.
- **Firmware** (`firmware/Cargo.toml`): built with the Xtensa toolchain from `espup`, target
  `xtensa-esp32-espidf`, ESP-IDF version pinned in `firmware/.cargo/config.toml`; the build
  downloads ESP-IDF into `firmware/.embuild/` (ignored by git). Settings of ESP-IDF:
  `firmware/sdkconfig.defaults` (16 MB flash, PSRAM in the heap with allocations above 4 KB
  placed there and 64 KB of internal RAM kept for the network and DMA, mbedTLS buffers in PSRAM,
  chip revision 3 and later, long file names on the FAT partition). The cargo feature `sim`
  builds the image QEMU runs (the simulator and the fixtures inside); `flash-saves` builds the
  measuring image, which `scripts/box.sh` flashes on the Dongle Max; `radio` builds the radio
  image, in its own target folder (`CARGO_TARGET_DIR=target/radio`) with
  `firmware/sdkconfig.radio.defaults` read after `sdkconfig.defaults` (the UART interrupt in
  internal RAM, the WebSocket and its post-handshake callback, the server's request head, the lwIP socket table of 16 and its
  core pinning, the PSRAM stacks and Wi-Fi and lwIP buffers, SNTP's servers), never together with
  `sim`; the feature `scripts` (`solite-core/script-recipes`, `rquickjs` with `bindgen`, `allocator` and
  `parallel`) is part of `radio` and is added to `sim` for QEMU (`--features sim,scripts`, never to
  `flash-saves`); QuickJS's C sources are compiled with ESP-IDF's own Xtensa compiler (not espup's:
  its objects are big-endian) and `bindgen` reads ESP-IDF's headers: `firmware/.cargo/config.toml`
  sets `CC_xtensa_esp32_espidf`, `CFLAGS_xtensa_esp32_espidf` and
  `BINDGEN_EXTRA_CLANG_ARGS_xtensa_esp32_espidf` for them, relative to `firmware/` (the toolchain's
  folder `esp-14.2.0_20260121` under `.embuild/` is pinned there with ESP-IDF v5.5.5); the Xtensa
  target has no 64-bit atomics, so the core uses none; no script is built in
  (spec 042), and `firmware/build.rs` embeds `ui/dist` for `radio` only, through `crates/ui-embed`, so
  `ui/dist` is built before the radio image (`validate.sh` does it); `firmware/.cargo/config.toml` sets `CARGO_WORKSPACE_DIR` so the settings files and `.embuild` are found in `firmware/` whatever the target folder is; without them, the image is the box's. The partition table is `firmware/partitions.csv` (settings, two
  application slots of 4 MB, a data partition; decision D25), given to the box by `scripts/box.sh flash`, not
  through `sdkconfig.defaults`. `sh scripts/qemu.sh` builds that table, assembles a flash image
  with ESP-IDF's `esptool` with the application at the offset of the first slot, as the table
  gives it, and boots it in Espressif's QEMU (`qemu-system-xtensa`, installed into
  `firmware/.embuild/` by ESP-IDF's tool installer), with 2 MB of PSRAM, the data partition blank
  at every run; it fails on a panic, a reboot, a missing line, a heap peak of the engine above
  350 KB, a device of the home with no measure, a dropped radio callback or an internal RAM minimum free below 64 KB, and, for the script phase, a missing `recipes: script` line, three script instances peaking above 75 % of the memory limit, a stack (the engine thread's or the `script` thread's) with under 2 KB unused, an install step that did not end `install 200, boot load ok, uninstall 200`, or a `recipe` thread with under 2 KB of its 20 KB unused; `scripts/validate.sh` searches the ELF of the box's, the plain `sim` and the measuring images for QuickJS's `JS_NewRuntime` and fails if it is there, and checks it is in the radio image's and the script build's, and that the radio image's ELF holds no `id: "motion-light"` (the script build reads that source for its phase: it is the control of the search; `--box` boots the box's image instead). The wiring, the risks and the backup procedure of the box are
  in [hardware.md](hardware.md); the memory shared out item by item is in
  [memory-budget.md](memory-budget.md).
- **Update key**: `SOLITE_UPDATE_PUBLIC_KEY` (64 hex characters) is read at build time with
  `option_env!` by the host and the firmware; without it, a build refuses updates (503). The
  private key is never in the repository.
- **Unsafe code**: the core and the host forbid it; the firmware denies it, except in the small
  functions that call ESP-IDF's C functions, each with a `SAFETY` comment (decision D11).
- **Tools** (`tools/<name>/`): TypeScript run directly by Node 24, no build step; type-checked by
  `tsc`, tested with `node:test`.
- **Interface** (`ui/`): Vite builds `ui/dist/`, which the host serves and the radio image embeds; `npm run dev` proxies
  `/api` and `/ws` to a host on port 8080; `ui/scripts/check-bundle-budget.mjs` checks the
  first load against its budget.

## Data

The box's own image stores no data; the radio image keeps the engine's files, `zigbee.json` (the
network's backup, keys in plain text), `wifi.json` (the Wi-Fi name and password, in plain text, never in NVS), `auth.json` and its boot marker `booting` in `/data`. Between a restore and the next start, `/data` (and `solite-data/` on the Mac) also holds the staged copies `<name>.restore` of the files a restore replaces and the marker `restore.pending` that names them (the start applies them and removes both); a restored network leaves the one-shot mark `zigbee.restore` until the radio's network is up. On the Mac, the host keeps `zones.json`, `equipments.json`,
`recipes.json`, `settings.json` and `auth.json` (the account and its password hash, or `{"version":1}` without an account; written
within 2 seconds of a change under `--serve`), `devices.json` (Sowel's devices with their
data and orders, and each device's last network address and endpoint; definitions written within 2 seconds under `--serve`, at once with `--pair`, values every 10 minutes, everything on stop) and writes
`network.json` (the network's identifiers
and keys, mode 0600) to its data folder after forming a network; the radio keeps the network
itself in its own flash. Under `--serve`, the host also keeps its update slots in `update/` of the data folder (`slot-0.bin`, `slot-1.bin`, `boot.json`); the box keeps the images in its two application slots and the boot record in `otadata`. On the Mac, `tools/z2m-coverage/report.md` is the coverage
report, committed with the library version and date it measures.
